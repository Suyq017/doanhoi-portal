\section{Thiết kế hệ thống}

\subsection{Kiến trúc tổng thể}
Từ kết quả phân tích ở Chương 3, hệ thống được thiết kế theo hướng mô-đun hóa nghiệp vụ, tách biệt rõ lớp giao diện, lớp dịch vụ, lớp truy cập dữ liệu và lớp tích hợp hệ thống ngoài. Cách tiếp cận này giúp hệ thống vừa đáp ứng tốt yêu cầu hiện tại của cổng thông tin Đoàn -- Hội, vừa thuận lợi khi mở rộng thêm chức năng trong các giai đoạn tiếp theo.

\subsubsection{Kiến trúc logic nhiều lớp}
Về mặt logic, hệ thống được tổ chức theo bốn lớp chính:
\begin{itemize}
	\item \textbf{Lớp trình bày (Presentation Layer):} frontend sử dụng React + TypeScript, tổ chức theo các module chức năng như Người dùng, Tổ chức, CTXH, Thu phí, Biểu mẫu, Chatbot. Lớp này chịu trách nhiệm điều hướng, hiển thị dữ liệu, kiểm tra đầu vào phía client và tương tác API.
	\item \textbf{Lớp dịch vụ nghiệp vụ (Application/Business Layer):} backend sử dụng NestJS, triển khai theo module domain. Tại đây xử lý toàn bộ logic nghiệp vụ: xác thực, phân quyền, quản lý trạng thái nghiệp vụ, kiểm tra ràng buộc dữ liệu, và phối hợp các tiến trình nền.
	\item \textbf{Lớp dữ liệu (Data Layer):} sử dụng PostgreSQL làm kho dữ liệu giao dịch chính, truy cập thông qua TypeORM. Các quan hệ thực thể và ràng buộc toàn vẹn được quản lý tập trung tại backend.
	\item \textbf{Lớp tích hợp (Integration Layer):} tích hợp các dịch vụ ngoài như PayOS (thanh toán), S3-compatible storage (lưu file), dịch vụ mô hình ngôn ngữ và vector store cho chatbot RAG.
\end{itemize}

Việc phân lớp theo trách nhiệm giúp giảm phụ thuộc chéo giữa các thành phần, tăng khả năng kiểm thử độc lập và hạn chế rủi ro khi thay đổi một module cụ thể.

\subsubsection{Thiết kế backend theo module}
Backend được thiết kế theo mô hình module của NestJS, trong đó mỗi nhóm nghiệp vụ được đóng gói thành một module độc lập để dễ phát triển song song và tái sử dụng:
\begin{itemize}
	\item \textbf{Nhóm nền tảng:} \texttt{AuthModule}, \texttt{RolesModule}, \texttt{MetricsModule}, \texttt{AwsS3ConfigModule}.
	\item \textbf{Nhóm quản trị tổ chức -- nhân sự:} \texttt{UsersModule}, \texttt{OrganizationsModule}, \texttt{DepartmentsModule}, \texttt{ClassesModule}.
	\item \textbf{Nhóm dashboard và báo cáo điều hành:} \texttt{DashboardModule}.
	\item \textbf{Nhóm CTXH:} \texttt{CtxhModule} cho quản lý hoạt động/chấm điểm và \texttt{CtxhChatModule} cho tra cứu bằng RAG.
	\item \textbf{Nhóm thu phí:} \texttt{PaymentModule}, \texttt{PayosModule} xử lý campaign, assignment, fee level và đồng bộ trạng thái giao dịch.
	\item \textbf{Nhóm biểu mẫu:} \texttt{TemplatesModule} quản lý template Word, cấu hình field động và sinh tài liệu đầu ra.
\end{itemize}

Trong mỗi module, luồng xử lý tuân theo chuỗi Controller $\rightarrow$ Service $\rightarrow$ Repository/Entity. Cấu trúc này giúp phân tách rõ vai trò: controller nhận request, service hiện thực nghiệp vụ, repository thao tác dữ liệu.

\subsubsection{Thiết kế frontend và cơ chế giao tiếp}
Frontend sử dụng React + Vite, tổ chức theo hướng feature-based để bám theo các phân hệ nghiệp vụ. Quản lý trạng thái truy vấn và cache dữ liệu sử dụng \texttt{@tanstack/react-query}, nhờ đó giảm số lần gọi API lặp lại và tăng độ mượt của giao diện.

Giao tiếp frontend -- backend sử dụng REST API qua \texttt{axios}. Cơ chế xác thực dựa trên JWT và token refresh. Tại phía giao diện, các thành phần hiển thị được điều chỉnh theo danh sách quyền nhận từ backend, đảm bảo người dùng chỉ nhìn thấy chức năng nằm trong phạm vi vai trò được cấp.

\subsubsection{Kiến trúc triển khai và vận hành}
Hệ thống được đóng gói container và triển khai theo kiến trúc dịch vụ:
\begin{itemize}
	\item \textbf{Frontend container:} phục vụ ứng dụng React thông qua Nginx.
	\item \textbf{Backend container:} chạy ứng dụng NestJS, cung cấp API và xử lý nghiệp vụ.
	\item \textbf{PostgreSQL + pgvector:} lưu dữ liệu giao dịch và dữ liệu vector phục vụ RAG.
	\item \textbf{Redis/Bull Queue:} hỗ trợ các tác vụ nền và hàng đợi xử lý batch.
	\item \textbf{Prometheus + Grafana:} thu thập và trực quan hóa metrics vận hành.
\end{itemize}

Ở môi trường phát triển, hệ thống hỗ trợ thêm các thành phần tiện ích như pgAdmin và Ollama để kiểm thử cục bộ. Ở môi trường triển khai chính thức, cấu hình được tách riêng theo biến môi trường nhằm bảo đảm an toàn thông tin truy cập và thuận lợi khi chuyển môi trường.

\subsection{Thiết kế cơ sở dữ liệu}
Thiết kế cơ sở dữ liệu của hệ thống bám theo hướng domain-driven: mỗi phân hệ nghiệp vụ sở hữu nhóm bảng riêng, nhưng vẫn liên kết thống nhất thông qua các thực thể lõi như \texttt{users}, \texttt{organizations}. Cách tổ chức này giúp hệ thống vừa nhất quán về mặt dữ liệu, vừa giảm độ phức tạp khi truy vấn liên miền nghiệp vụ.

\subsubsection{Thiết kế cơ sở dữ liệu ý niệm}
Ở mức ý niệm, mô hình dữ liệu được chia thành sáu cụm nghiệp vụ chính:

\textbf{1. Cụm người dùng -- tổ chức}
\begin{itemize}
	\item \texttt{users} lưu thông tin định danh, học vụ, trạng thái thành viên, thông tin xác thực.
	\item \texttt{organizations} mô hình hóa cây tổ chức phân cấp (Trường/Khoa/Lớp/Đoàn/Hội/CLB).
	\item \texttt{user\_organizations} biểu diễn quan hệ nhiều-nhiều giữa người dùng và tổ chức, kèm vai trò thành viên trong đơn vị.
	\item \texttt{departments}, \texttt{classes} biểu diễn khoa và lớp phục vụ quản lý học vụ.
\end{itemize}

\textbf{2. Cụm RBAC phân quyền}
\begin{itemize}
	\item \texttt{permissions} định nghĩa đơn vị quyền thao tác.
	\item \texttt{roles} gom nhóm các quyền theo vai trò nghiệp vụ.
	\item \texttt{user\_roles} gán vai trò cho người dùng theo ngữ cảnh toàn cục hoặc theo tổ chức.
\end{itemize}
Mô hình này cho phép một người dùng giữ nhiều vai trò khác nhau ở các đơn vị khác nhau, đúng với thực tế vận hành Đoàn -- Hội đa cấp.

\textbf{3. Cụm CTXH}
\begin{itemize}
	\item \texttt{ctxh\_category} quản lý danh mục hoạt động.
	\item \texttt{ctxh\_activity} quản lý thông tin hoạt động và vòng đời trạng thái.
	\item \texttt{ctxh\_participation} lưu kết quả tham gia/chấm điểm của từng sinh viên theo hoạt động.
	\item \texttt{ctxh\_limit\_config} lưu cấu hình giới hạn số ngày CTXH theo tổ chức.
\end{itemize}

\textbf{4. Cụm thu phí}
\begin{itemize}
	\item \texttt{payment\_campaigns} đại diện các đợt thu theo tổ chức.
	\item \texttt{payment\_fee\_levels} cấu hình mức phí áp dụng cho campaign.
	\item \texttt{payment\_assignments} gán nghĩa vụ đóng phí cho từng người dùng.
	\item \texttt{payment\_history} lưu lịch sử giao dịch và trạng thái thanh toán.
	\item \texttt{payment\_campaign\_payos\_configs} lưu cấu hình PayOS theo chiến dịch/tổ chức.
\end{itemize}

\textbf{5. Cụm biểu mẫu}
\begin{itemize}
	\item \texttt{templates} lưu metadata của mẫu \texttt{.docx} và kết quả parse schema.
	\item \texttt{template\_fields} lưu cấu hình trường động, validation, thứ tự hiển thị.
	\item \texttt{template\_submissions} lưu dữ liệu người dùng nộp và file đầu ra đã render.
\end{itemize}

\textbf{6. Cụm dữ liệu RAG}
\begin{itemize}
	\item \texttt{ctxh\_embeddings} lưu các vector embedding theo từng hoạt động và từng chunk nội dung.
	\item Bảng này liên kết về \texttt{ctxh\_activity}, là cầu nối giữa dữ liệu nghiệp vụ CTXH và lớp truy xuất ngữ nghĩa.
\end{itemize}

\subsubsection{Thiết kế cơ sở dữ liệu vật lý}
Ở mức vật lý, hệ thống sử dụng PostgreSQL với các đặc trưng chính sau:

\textbf{1. Quy ước khóa và kiểu dữ liệu}
\begin{itemize}
	\item Khóa chính của các bảng nghiệp vụ dùng \texttt{UUID}, phù hợp cho hệ phân tán và giảm nguy cơ lộ thông tin tuần tự.
	\item Trường thời gian dùng \texttt{timestamp} và được quản lý bởi các cột audit như \texttt{created\_at}, \texttt{updated\_at}, \texttt{deleted\_at}.
	\item Các trường trạng thái dùng \texttt{ENUM} để ép ràng buộc miền giá trị ngay tại tầng dữ liệu.
\end{itemize}

\textbf{2. Ràng buộc toàn vẹn và quan hệ}
\begin{itemize}
	\item Các quan hệ lõi được ràng buộc bằng foreign key, đi kèm chính sách \texttt{CASCADE} ở những nơi cần dọn dẹp dữ liệu phụ thuộc (ví dụ quan hệ user-role, user-organization, embedding-activity).
	\item Với phân quyền, bảng \texttt{user\_roles} đặt unique index trên bộ \texttt{(userId, roleId, organizationId)} để chống gán trùng vai trò trong cùng phạm vi.
	\item Với cây tổ chức, hệ thống sử dụng mô hình \texttt{closure-table} để tối ưu truy vấn tổ tiên/hậu duệ trong cấu trúc phân cấp nhiều mức.
\end{itemize}

\textbf{3. Chỉ mục và tối ưu truy vấn}
\begin{itemize}
	\item Các bảng nghiệp vụ có chỉ mục theo cột truy vấn thường xuyên như \texttt{activity\_id}, \texttt{created\_at}, tổ hợp \texttt{(templateId, status)}, \texttt{(userId, createdAt)}.
	\item Dữ liệu vector trong \texttt{ctxh\_embeddings} sử dụng kiểu \texttt{vector(1024)}; chỉ mục HNSW với \texttt{vector\_cosine\_ops} được dùng để tăng tốc truy vấn tương tự cho chatbot.
	\item Metadata của embeddings lưu dạng \texttt{jsonb} và được bổ sung GIN index để hỗ trợ lọc theo thuộc tính ngữ cảnh.
\end{itemize}

\textbf{4. Cấu trúc dữ liệu theo trạng thái nghiệp vụ}
Các bảng quan trọng đều biểu diễn vòng đời xử lý thông qua cột trạng thái, ví dụ:
\begin{itemize}
	\item \texttt{ctxh\_activity}: \texttt{DRAFT}, \texttt{ACTIVE}, \texttt{COMPLETED}, \texttt{CANCELLED}.
	\item \texttt{payment\_campaigns}: \texttt{DRAFT}, \texttt{ACTIVE}, \texttt{COMPLETED}, \texttt{CANCELLED}.
	\item \texttt{payment\_assignments}: \texttt{PENDING}, \texttt{PAID}, \texttt{OVERDUE}, \texttt{EXEMPTED}.
	\item \texttt{template\_submissions}: \texttt{draft}, \texttt{submitted}, \texttt{completed}, \texttt{failed}.
\end{itemize}
Thiết kế này giúp backend hiện thực rõ ràng các luật chuyển trạng thái và giảm rủi ro cập nhật dữ liệu sai ngữ cảnh nghiệp vụ.

\textbf{5. Mở rộng và bảo trì dữ liệu}
Mô hình dữ liệu hiện tại đã được chuẩn hóa ở mức phù hợp cho hệ thống vận hành thực tế: tách riêng bảng theo miền nghiệp vụ, dùng khóa ngoại để bảo toàn quan hệ, và có không gian mở rộng cho các tính năng mới (thêm module mới, thêm thuộc tính metadata, mở rộng quy tắc phân quyền theo ngữ cảnh).

Nhờ đó, khi hệ thống tăng quy mô người dùng và khối lượng giao dịch, kiến trúc dữ liệu vẫn duy trì được tính nhất quán, khả năng truy vấn và mức độ dễ bảo trì.

\subsubsection{Thiết kế dữ liệu phục vụ Chatbot RAG}
Bên cạnh dữ liệu giao dịch, hệ thống duy trì một lớp dữ liệu truy xuất ngữ nghĩa để hỗ trợ chatbot hỏi-đáp CTXH. Lớp dữ liệu này được thiết kế nhằm bảo đảm ba mục tiêu đồng thời: (1) truy vấn đúng ngữ cảnh câu hỏi tự nhiên, (2) truy vết được nguồn trả lời, (3) cập nhật linh hoạt khi dữ liệu hoạt động thay đổi.

\textbf{1. Nguồn dữ liệu đầu vào cho RAG}
Nguồn dữ liệu gốc lấy từ thực thể hoạt động CTXH và các thực thể liên quan (danh mục, tổ chức). Các thuộc tính nghiệp vụ quan trọng được chuẩn hóa trước khi tạo embedding gồm:
\begin{itemize}
	\item \texttt{id}, \texttt{name}, \texttt{description}
	\item \texttt{category.id}, \texttt{category.name}
	\item \texttt{organization.id}, \texttt{organization.name}
	\item \texttt{start\_date}, \texttt{end\_date}, \texttt{total\_days}, \texttt{location}
	\item \texttt{status}
\end{itemize}

\textbf{2. Bảng lưu vector và metadata}
Hệ thống sử dụng bảng \texttt{ctxh\_embeddings} để lưu:
\begin{itemize}
	\item Nội dung text đã chuẩn hóa để nhúng vector (\texttt{content\_text})
	\item Vector embedding (kiểu \texttt{vector})
	\item Chỉ số phân mảnh nội dung (\texttt{chunk\_index})
	\item Metadata phục vụ lọc theo ngữ cảnh thời gian, tổ chức, danh mục, trạng thái
\end{itemize}
Thiết kế này cho phép vừa tìm kiếm ngữ nghĩa theo độ tương đồng vector, vừa lọc logic theo ràng buộc nghiệp vụ mà người dùng đặt ra trong câu hỏi.

\textbf{3. Mẫu chuẩn hóa văn bản trước khi embedding}
Để tăng tính nhất quán ngữ nghĩa giữa các bản ghi hoạt động, hệ thống sử dụng mẫu hợp nhất các thuộc tính chính thành một đoạn văn chuẩn trước khi sinh embedding, ví dụ:
\begin{quote}
Tên hoạt động: [name], Mô tả: [description], Danh mục: [category.name],\\
Tổ chức: [organization.name], Thời gian: Từ [start\_date] đến [end\_date],\\
Ngày CTXH được cấp: [total\_days] ngày, Địa điểm: [location]
\end{quote}
Mẫu này giúp giảm sai lệch định dạng giữa các bản ghi, từ đó ổn định chất lượng retrieval khi người dùng đặt câu hỏi đa dạng.

\textbf{4. Cập nhật dữ liệu RAG theo vòng đời hoạt động}
Khi dữ liệu hoạt động CTXH thay đổi, lớp vector cần được đồng bộ tương ứng. Thiết kế hiện tại hỗ trợ:
\begin{itemize}
	\item Tạo mới embeddings khi thêm hoạt động mới đủ điều kiện nghiệp vụ.
	\item Tái tạo embeddings khi các trường ngữ nghĩa quan trọng của hoạt động được cập nhật.
	\item Xóa embeddings liên quan khi hoạt động bị xóa hoặc không còn phù hợp cho truy xuất.
\end{itemize}
Ngoài cơ chế đồng bộ theo sự kiện, hệ thống còn hỗ trợ các tác vụ ingestion toàn phần và incremental để bảo trì định kỳ hoặc khởi tạo lại vector store khi cần.

\textbf{5. Vai trò của lớp dữ liệu RAG trong toàn hệ thống}
Lớp dữ liệu RAG không thay thế dữ liệu giao dịch chính mà đóng vai trò chỉ mục ngữ nghĩa phục vụ truy vấn hội thoại. Nhờ tách lớp như vậy, hệ thống vừa giữ được tính toàn vẹn của dữ liệu nghiệp vụ ở PostgreSQL, vừa cung cấp khả năng hỏi-đáp linh hoạt theo ngôn ngữ tự nhiên cho người dùng cuối.

\subsection{Các quyết định thiết kế và trade-off}
Trong quá trình hiện thực, nhóm không chỉ lựa chọn công nghệ theo tiêu chí phổ biến mà còn cân nhắc rõ các đánh đổi kỹ thuật (trade-off) giữa hiệu năng, độ phức tạp triển khai, khả năng mở rộng và chi phí vận hành.

\subsubsection{Tách module nghiệp vụ so với kiến trúc nguyên khối}
\textbf{Quyết định:} sử dụng kiến trúc module trong cùng một backend NestJS thay vì một codebase nguyên khối không phân lớp.

\textbf{Lợi ích:}
\begin{itemize}
	\item Tăng khả năng phát triển song song giữa các nhóm.
	\item Tái sử dụng được service chung (auth, roles, metrics, storage).
	\item Dễ khoanh vùng lỗi khi có sự cố ở từng nghiệp vụ.
\end{itemize}

\textbf{Đánh đổi:}
\begin{itemize}
	\item Cần quản trị chặt dependency giữa các module để tránh vòng phụ thuộc.
	\item Cần thống nhất conventions DTO, response schema và guard để không phân mảnh.
\end{itemize}

\subsubsection{RBAC theo ngữ cảnh tổ chức so với phân quyền toàn cục}
\textbf{Quyết định:} dùng mô hình \texttt{user\_roles} có \texttt{organizationId} tùy chọn thay vì chỉ gán role toàn hệ thống.

\textbf{Lợi ích:}
\begin{itemize}
	\item Phản ánh đúng cấu trúc Đoàn -- Hội nhiều cấp.
	\item Một tài khoản có thể đảm nhiệm vai trò khác nhau ở các đơn vị khác nhau.
	\item Giảm rủi ro cấp quyền quá rộng so với nhu cầu nghiệp vụ thực.
\end{itemize}

\textbf{Đánh đổi:}
\begin{itemize}
	\item Truy vấn quyền phức tạp hơn (phải xét context).
	\item Frontend cần nhận diện rõ phạm vi quyền để hiển thị đúng chức năng.
\end{itemize}

\subsubsection{PostgreSQL + pgvector so với tách riêng vector database}
\textbf{Quyết định:} lưu dữ liệu giao dịch và dữ liệu vector trong cùng nền PostgreSQL, sử dụng extension pgvector.

\textbf{Lợi ích:}
\begin{itemize}
	\item Giảm độ phức tạp hạ tầng so với vận hành thêm một vector DB độc lập.
	\item Dễ đồng bộ khóa ngoại giữa \texttt{ctxh\_activity} và \texttt{ctxh\_embeddings}.
	\item Thuận lợi backup/restore toàn bộ hệ thống dữ liệu.
\end{itemize}

\textbf{Đánh đổi:}
\begin{itemize}
	\item Khi dữ liệu vector tăng mạnh, cần tinh chỉnh chỉ mục và chiến lược ingestion kỹ hơn.
	\item Cần cân bằng tài nguyên giữa workload OLTP và workload semantic search.
\end{itemize}

\subsubsection{Batch processing cho import dữ liệu lớn}
\textbf{Quyết định:} dùng batch + retry/fallback thay vì xử lý một transaction khổng lồ cho toàn file.

\textbf{Lợi ích:}
\begin{itemize}
	\item Hạn chế timeout với file lớn.
	\item Cô lập lỗi theo lô, dễ rollback cục bộ và báo cáo lỗi rõ hơn.
	\item Cải thiện trải nghiệm người dùng qua trạng thái tiến trình.
\end{itemize}

\textbf{Đánh đổi:}
\begin{itemize}
	\item Tăng độ phức tạp logic điều phối phiên import.
	\item Cần kiểm soát tính nhất quán khi có retry hoặc dừng giữa chừng.
\end{itemize}

\subsubsection{Template động + lưu file S3 so với lưu BLOB trong database}
\textbf{Quyết định:} tách metadata trong PostgreSQL và lưu file Word đầu vào/đầu ra trên S3-compatible storage.

\textbf{Lợi ích:}
\begin{itemize}
	\item Giảm tải kích thước dữ liệu trong DB giao dịch.
	\item Tăng khả năng mở rộng dung lượng tài liệu dài hạn.
	\item Dễ triển khai chính sách lifecycle và backup cho file.
\end{itemize}

\textbf{Đánh đổi:}
\begin{itemize}
	\item Cần cơ chế đồng bộ trạng thái giữa metadata và file thật.
	\item Cần kiểm soát quyền truy cập URL file đầu ra.
\end{itemize}

Nhìn chung, các quyết định trên cho thấy hệ thống ưu tiên tính khả thi triển khai và độ ổn định vận hành trong bối cảnh nghiệp vụ thực của nhà trường, đồng thời vẫn giữ biên mở rộng đủ lớn cho các yêu cầu nâng cấp ở giai đoạn sau.
